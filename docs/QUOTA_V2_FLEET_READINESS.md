# Квоты v2 — предварительная проверка совместимости нод

## Текущее состояние

`XMESH_QUOTA_V2_ENABLED` остаётся выключенным по умолчанию. Текущий одноразовый E2E-стенд проверяет Node `control-v6.0.27` при `1`, но это **не** доказывает, что все установленные ноды или все Xray-обработчики в production готовы. Пока нет авторитетного подписанного *финального* счётчика Xray, автоматический досрочный возврат резерва запрещён; консервативное списание и отсутствие возврата остаются безопасной альтернативой.

## Запрос готовности

Авторизованный оператор с правами управления нодами может получить отчёт:

```http
GET /api/v1/quota-v2/fleet-readiness
```

В `nodes` для каждой ноды показаны:

- `reportedProtocolVersion`: версия из **аутентифицированного** запроса ноды (Ed25519 либо доверенный XSP-v2 product gateway) `/api/v1/node/desired-config`; отсутствие версии сохраняется как `0`.
- `lastAuthenticatedRequestAtMs`, `recentAuthenticatedRequest`: отметка последнего аутентифицированного обращения, годного только **15 минут**.
- `legacyQuietPeriodPassed`, `lastLegacyAuthenticatedRequestAtMs`: подтверждение отсутствия аутентифицированных обращений старого протокола за последние **15 минут**; проверка не позволяет смешанному парку v1/v2 выглядеть полностью готовым.
- `signedPolicyServedAfterClaim`: после данного обращения Nexus действительно сформировал и выдал подписанную политику.
- `reportedAgentVersion`, `lastAuthenticatedAgentHeartbeatAtMs`, `agentHeartbeatFresh`: версия управляющего Agent из прошедшего Node-аутентификацию heartbeat (не показание бинарного аттестатора), срок годности **65 секунд**. Heartbeat отдельного маршрутизатора `0.1.0` не подменяет версию Agent.
- `legacyAgentQuietPeriodPassed`, `lastOutdatedAgentHeartbeatAtMs`: в течение предыдущих **15 минут** нельзя получать обращения старой версии управляющего Agent. Одно обращение `control-v6.0.27` не скрывает работающий параллельно `control-v6.0.23`.
- `agentReleasePreflightPassed`, `agentBlocker`: сравнение с текущим серверным `targetAgentVersion`. Причины: `missing_or_stale_authenticated_agent_heartbeat`, `agent_release_version_mismatch`, `outdated_agent_seen_recently`, `none`.
- `rolloutPreflightPassed`: для отдельной ноды одновременно прошли проверка протокола v2 **и** проверка версии/свежести Agent. Поле в корне становится `true`, только когда это выполнили **все** неотключённые ноды. `rolloutCompatibleNodes` показывает количество прошедших проверку.
- `protocolPreflightPassed` и `blocker`: причины незавершённой проверки `missing_or_stale_authenticated_request`, `legacy_or_missing_protocol_v2`, `legacy_protocol_seen_recently`, `no_signed_policy_served_after_claim` либо `none`. Выключенные ноды обозначены `excluded_disabled` и исключены из числа обслуживающих.

Поле `protocolPreflightPassed` в корне становится `true` лишь тогда, когда **каждая** неотключённая нода недавно аутентифицировала запрос v2 и после него получила подписанную конфигурацию. Кроме того, в течение последних **15 минут** не должно быть ни одного аутентифицированного запроса старого протокола от этой ноды: один новый запрос v2 не скрывает параллельно работающий старый Agent. Пустой парк не считается готовым. Если нода снова аутентифицирует v1-запрос, статус немедленно ухудшается, даже если раньше она была v2; последующий v2-запрос сам по себе не отменяет 15-минутный период ожидания. Секреты и приватные ключи в отчёте отсутствуют. Неавторизованный запрос запрещён.

**Важно:** `protocolPreflightPassed` отвечает только за совместимость протокола и может быть `true` даже при устаревшем Agent. Для проверки обновления парка используйте более строгий `rolloutPreflightPassed`, учитывающий heartbeat. Это всё равно **только предварительная проверка**, а не разрешение активировать квоты или возвращать трафик.

**Проверка применения на Xray (не только доставки):** `applicationPreflightPassed` требует, чтобы на каждой обслуживающей ноде после последней доставки подписанной конфигурации был свежий (≤65 с) Node-аутентифицированный heartbeat с `xrayRunning=true`, `runtimeProfileCheck=verified` и `reportedAppliedRevision`, равной `lastServedRevision` из БД Nexus. Отдельное поле `activationCandidatePreflightPassed` требует одновременно готовности протокола, версии Agent **и** такого подтверждения применения на всех обслуживающих нодах. `applicationBlocker` содержит конкретную причину: `missing_or_stale_authenticated_runtime_heartbeat`, `xray_not_running`, `active_profile_not_verified`, `last_served_revision_not_applied` либо `no_application_heartbeat_after_policy_delivery`. Ревизия из `node_desired_revisions` означает последнюю **выданную** конфигурацию. Дополнительно для нод с уже пройденным подтверждением применения Nexus **заново компилирует** актуальную конфигурацию из настроек панели без выдачи новой политики: поля `currentProfileRecompiled` и `currentAuthoritativeRevision`. Если текущая ревизия не совпала с применённой, `applicationBlocker=current_profile_revision_not_applied`; при ошибке компиляции — `current_profile_compile_failed`. Оба случая блокируют `applicationPreflightPassed` и `activationCandidatePreflightPassed` (но не меняют уже выданные лимиты).

Подписанный heartbeat всё ещё **не является** независимой аттестацией исполняемого файла, доказательством полного завершения физических потоков Xray или финальным счётчиком. Даже `activationCandidatePreflightPassed=true` сам по себе не меняет `XMESH_QUOTA_V2_ENABLED` и не разрешает возврат резервов.

## Атомарный расчёт по будущему финальному счётчику — только в CI

`scripts/test-quota-v2-postgres.py` проверяет отдельно от Xray **спящую** SQL-функцию `quota_v2_settle_verified_terminal` на одноразовой PostgreSQL: 12 одновременных одинаковых повторов финальной квитанции, восемь несовместимых конкурирующих подтверждений одной резервации, состязание финального расчёта с консервативным списанием и отсутствие привилегий у посторонней SQL-роли. Во всех случаях одна резервация не может освободить байты дважды; если раньше прошло консервативное списание, возврат не допускается. Если первая проверенная запись победила, другой ноде доступна только действительно освобождённая разница, а не сумма повторных запросов.

**Это не физическая проверка Xray.** Тест напрямую вызывает SQL от имени владельца миграций с гипотетически проверенными числами, а не принимает API-квитанции. Он проверяет безопасность будущего атомарного расчёта, но никак не разрешает включать `XMESH_QUOTA_V2_ENABLED`, вызывать функцию из HTTP или считать остановку ноды доказательством финальности.

## Граница между обычными квитанциями и финальным счётчиком

Подписанная нодой `quotaStopReceipts` подтверждает, что управляющая конфигурация была применена, **но не подтверждает последнюю запись счётчиков Xray**. Обычные `quotaReceipts` — только накопленные показания. Поэтому `POST /api/v1/metrics/ingest` принимает их по существующей схеме, но теперь **отклоняет HTTP 400** любые верхнеуровневые попытки прислать `quotaTerminalReceipts`, `terminalReceipt`, `finalMeterVerified`, `settlementEligible` или `refundableBytes` (включая snake_case и даже `null`/`0`). Поле финальности внутри `quotaStopReceipts` также запрещено строгой схемой.

Такой отклонённый запрос не должен изменять ни пользовательский счётчик, ни резервы PostgreSQL, ни `quota_v2_terminal_settlements`. Проверка включена в E2E с настоящей Ed25519-подписью двух независимых нод. Отдельный протокол терминального доказательства пока **не реализован**: SQL-процедура `quota_v2_settle_verified_terminal` не вызывается из HTTP, и преждевременное уменьшение обязательств или возврат трафика запрещены. Для реализации понадобятся проверяемое завершение всех Xray-потоков и монотонные финальные байты, независимое подтверждение и защита от replay (Node issue #109, Nexus issue #509).

## Что этот отчёт НЕ доказывает

Аутентифицированный запрос подтверждает только Node Ed25519-ключ либо авторизацию доверенного product gateway. Самостоятельно он не удостоверяет версию установленного бинарника Agent, применение политики всеми работающими процессами и фактическую остановку Xray, сохранении последних байтов после сбоя или возможности возвращать резерв. Поэтому отчёт намеренно содержит:

- `installedAgentVersionAttested: false`
- `physicalStopAndFinalMeterVerified: false`
- `canRefundFromThisPreflight: false`
- `requiresNodeRolloutVerification: true`

**Нельзя автоматически менять `XMESH_QUOTA_V2_ENABLED` только на основании этого отчёта.** До переключения нужно независимо сверить фактически установленный Agent всех действующих нод, проверить подписанное применение политики и отсутствие старых выданных лимитов, пройти тестовый сценарий обновления/отката и доказать конечный учёт для полного набора транспортов. Нельзя принимать наблюдаемые (нефинальные) снимки Xray за подписанные терминальные доказательства.

## Зачем сохранять версии старых запросов

При включённом флаге Nexus отклоняет старый запрос без `quotaProtocolVersion=2` с HTTP 409 **до выдачи нового резерва**. Без проверки всего парка старые ноды потеряют возможность обновлять политику. Миграция `0130_quota_v2_authenticated_protocol_observations.sql` хранит сведения о протоколе, а `0131_quota_v2_authenticated_agent_release_observations.sql` — отдельно о версиях из аутентифицированных heartbeat и моментах работы старого управляющего Agent. Ни одна из них не управляет выдачей квот и не включает флаг. При обновлении уже действующей панели миграция 0131 переносит свежие heartbeat управляющих нод в новый журнал и консервативно требует 15 минут без старой версии даже тогда, когда последний heartbeat уже сообщает `control-v6.0.27`: параллельные старые процессы до миграции невозможно исключить по одному снимку.

Двухнодовый CI использует закреплённый код Node `control-v6.0.27` (`5de71f4abe42`). Он дополнительно запускает проверки липких меток потери непрерывности и сохранения общего/покомпонентного накопленного трафика (только НЕФИНАЛЬНЫЕ снимки). `scripts/test-quota-v2-e2e.py` проверяет пустую историю, неавторизованный запрос оператора, старый протокол, одну и две v2-ноды, устаревшую запись, повторное обращение и откат к старому протоколу. Тест запускается только на одноразовом Docker/PostgreSQL стенде.

Проверка на одноразовом стенде также включает аутентифицированные heartbeat старой/новой версии, период сосуществования двух поколений, устаревшие heartbeat, попытку выдать версию другой ноды и защитное заполнение нового журнала из heartbeat старой панели. Запросы первых подтверждённых офлайн-резервов от двух **разных Ed25519-нод** и их повторные запросы после потерянного HTTP-ответа выполняются действительно одновременно (барьер двух потоков, раздельные ключи и журналы), с проверкой неизменности резервов и глобального `settled + held ≤ paid limit`. Даже успешный отчёт не делает разрешёнными автоматические досрочные возвраты резервов. Экспериментальные Xray-снимки не являются финальным счётчиком и не разблокируют автоматический возврат. Консервативное списание неиспользованного резерва не возмещает его повторно.

## Операционная проверка старых VPS (только чтение)

**Не допускайте замкнутого требования «всё уже на v2 до включения v2».** Пока `XMESH_QUOTA_V2_ENABLED=0`, Nexus **умышленно подписывает версию политики 1**. Только после одобренного переключения серверный `apply_quota_v2_if_enabled` начнёт подписывать v2-резервы. Поэтому на всех уже обновлённых VPS предусмотрены **две отдельные фазы аудита** (нужен Node с новым двухфазным скриптом, см. закреплённый SHA ниже).

**Фаза 1 — до включения флага, только проверка установленного runtime**:

```bash
sudo python3 /opt/xmesh-node/scripts/quota-v2-local-audit.py --json --phase runtime
```

Нужно получить `localRuntimePreflightPassed=true` и `runtimeBlockers=[]` на **каждом** обслуживающем VPS. При текущем серверном флаге `0` нормальны `localPolicyVersion=1`, `v2PolicyStillPending=true` и `localV2AppliedVerified=false`. Наличие работающих текущих Agent, signed guard, Xray, пользовательского meter-таймера и их проверенных байтов ещё **не** означает, что старые подписанные v1-политики отозваны. Поле `potentialLiveV1OfflineBudget=true` прямо указывает на риск активного старого бюджета; его `false` не доказывает отсутствие других копий v1-политики/сессий. Никакой зелёный runtime-отчёт не разрешает автоматически выставить флаг `1`.

Параллельно проверяйте через авторизованный `GET /api/v1/quota-v2/fleet-readiness` свежий `activationCandidatePreflightPassed`, отсутствие старых v1-запросов/старых Agent за 15 минут, точное соответствие применённой ревизии и все выключенные/удалённые VPS за пределами отчёта. Это только проверки готовности: до решения о переключении оператор отдельно подтверждает вывод старых Xray, устранение ВСЕХ автономных копий v1-политик и возможность безопасного прекращения доступа. Никакого ослабления проверки или автоматического возврата резерва при этом нет.

**Фаза 2 — только после отдельного одобренного переключения и пересогласования всех нод**:

```bash
sudo python3 /opt/xmesh-node/scripts/quota-v2-local-audit.py --json --phase applied
```

Требуется `localV2AppliedVerified=true` на каждой обслуживающей ноде: только тогда проверен фактически применённый signed v2 профиль. Старый вызов `--json` без `--phase` сохраняет безопасное поведение фазы `applied` и код выхода 1 при v1. **Обычный откат флага к `0` после выдачи v2-политик не является безопасным возвратом к v1.** Nexus теперь проверяет постоянный глобальный журнал `quota_v2_reservations`: если хоть одна v2-резервация когда-либо была выдана, при отключённом флаге `/node/desired-config` отвечает **HTTP 409** и не подписывает v1-политику **ни старой, ни новой ноде**. Уже действующие v2-резервы при этом НЕ возвращаются и НЕ стираются. Guard независимо отклоняет повторную отправку сохранённой подписанной v1-политики после v2. Node может завершить обслуживание, когда истечёт последний проверенный офлайн-бюджет. Для продолжения сервиса требуется вернуть корректный режим v2 и выполнить безопасное согласование; сброс переменной на `0` не является поддерживаемым rollback. План обратного перехода требует отдельно утверждённого протокола миграции и проверки на стенде.

Оба отчёта всегда сохраняют `fleetActivationAuthorized=false`, `allLegacyCopiesRetiredVerified=false`, `finalMeterVerified=false` и `refundableBytes=0`. Нефинальные счётчики и уведомления об остановке Xray не дают права возвращать байты.

Результат показывает `localV2AppliedVerified`, `localPolicyVersion`, `potentialLiveV1OfflineBudget` и безопасные к разглашению фиксированные `blockers`. Проверяется локальный подписанный профиль против реального управляемого Xray, версии исполняемых файлов Agent по фактическому SHA-256 и установленному манифесту, а также активность и включение **четырёх** таймеров контроля/учёта (`xmesh-node-control.timer`, `xmesh-xray-sync.timer`, `xmesh-node-metrics.timer`, `xmesh-node-user-meter.timer`), отсутствие **любых дополнительных Docker-контейнеров, включая остановленные** (их необходимо рассматривать как потенциально возобновляемые старые процессы), и отсутствие старых нативных `xray.service` / `v2ray.service`. Проверяются **фактические Docker-состояния**, а не только имена контейнеров: остановленный `xmesh-node` или `xmesh-managed-xray` теперь блокирует локальную готовность, даже если контейнер существует в `docker ps --all`. Читаются только состояние и статусы, ничего не останавливается и не меняется. Любая v1-политика блокирует успешную **локальную** проверку — включая истёкшую, а при неистёкшей с офлайн-лимитом явно отмечается потенциально активный старый бюджет.

Аудит также сверяет фактически установленные `xmesh-xray-sync`, оба слоя `policy-guard`, помощник ревокации, аттестатор профиля, strict-PQ транспортный адаптер и hot-user reconciler с **байтами проверенного локального Git checkout**, привязанного к `sourceRevision` PQ-манифеста. Несовпадение SHA-256, изменённый checkout или старый скрипт дают `installed_quota_enforcement_worker_unverified` и запрещают считать ноду готовой. Этот тест ничего не меняет на VPS. Отдельно требуется активный таймер персонального счётчика `xmesh-node-user-meter.timer`: наличие работающего Xray и общего heartbeat не доказывает запись пользовательских байтов.\n\n**ВАЖНО:** даже локальный зелёный результат не доказывает, что нет другого контейнера, старого удалённого Xray, склонированного ключа или отключённой ноды. Утилита всегда возвращает `fleetActivationAuthorized=false`, `allLegacyCopiesRetiredVerified=false` и `refundableBytes=0`. Включение `1` остаётся ручной операцией после проверки всего физического парка и сценария отката; это не кнопка автоматической активации.

**Обязательная защита:** Node `control-v6.0.27` устанавливает аварийную остановку Xray ещё до чтения ключей и журналов и запрещает запуск без подписанного guard (даже при HTTP 200); также отказывает в обслуживании при недоступности Nexus и отсутствии автономного guard; физически выключает управляемый Xray и отключает Docker autorestart при истекшей/непроверяемой кэшированной политике, недоступном offline guard, непроверяемом StatsService и любой неудаче офлайн-пересогласования. Старую конфигурацию при такой ошибке больше нельзя автоматически восстановить. Результат STOP — это защита допуска, а **не** терминальный подписанный счётчик и не основание возвращать зарезервированные байты. Проверка всех реально установленных VPS остаётся обязательной.

## Приёмка обновления и остановка rollout

1. На отдельных одноразовых стендах прогоните установку с пустого состояния и обновление с точных текущих версий Nexus, Agent и Xray. Зафиксируйте SHA всех компонентов и миграций, владельцев каталогов WAL и сокетов, `ProtectSystem=strict` и состояние сервисов после перезагрузки.
2. Перед первой выдачей проверьте отчёт готовности парка и аудит каждой обслуживающей ноды. Сделайте проверяемую резервную копию PostgreSQL и сохраните ключи доверия, WAL, подписанные квитанции и состояние ingress. Проверьте восстановление из копии в отдельной среде.
3. С разрешения владельца включите v2 сначала в отдельной установке Nexus с пилотными нодами. Флаг Nexus действует глобально в пределах установки. Подтвердите signed v2 на каждой ноде, реальный VLESS через три поколения, независимость пользователей, сохранность резерва после повторов и отказ в доступе при непроверенном runtime.
4. Остановите расширение при несовместимости схемы или версий, расхождении списаний, сбое проверки подписи или WAL либо неподтверждённом маршруте ingress. Закройте затронутый пользовательский ingress, сохраните историю и восстанавливайте обслуживание на совместимых версиях после сверки с Nexus.
5. После первой v2-выдачи обычная переустановка Agent, прежний бинарник Nexus поверх новой схемы и возврат маршрута на прежний Xray требуют отдельной проверки совместимости. Снимок БД, сделанный до выдачи, нельзя использовать для возобновления трафика: он исключает последующие резервы и списания. При невозможности доказать непрерывность учёта доступ остаётся закрытым.

Для аварийной остановки выдачи на уже активированном стенде сохраните `XMESH_QUOTA_V2_ENABLED=1` и `XMESH_QUOTA_V2_WAL_TRANSPORT=1`. Задайте `XMESH_QUOTA_V2_PAUSE_ISSUANCE=1` и пересоздайте сервис Nexus командой `docker compose up -d --no-deps --force-recreate panel`. Если экземпляров Nexus несколько, остановите выдачу на каждом из них и проверьте `issuancePaused=true` в авторизованном отчёте готовности. Изменение файла окружения действует после пересоздания процесса.

В этом режиме Nexus отклоняет новые резервы и подписанные прибавки к лимитам кодом HTTP 503. Списания по WAL и проверенные повторы ранее сохранённых ответов продолжаются. Уже установленные разрешения действуют в пределах собственных лимитов и сроков. Для возобновления выдачи после сверки WAL и резервов задайте `XMESH_QUOTA_V2_PAUSE_ISSUANCE=0`, пересоздайте сервис и проверьте отчёт ещё раз.


## Сопоставление релизного кандидата с установленным E2E

Node CI сохраняет два Linux amd64 PQ-бинарника и `candidate-manifest.json` с точным исходным SHA, версией и SHA-256 каждого файла. Nexus CI сохраняет отдельный `installed-evidence.json` после каждого **успешного** сценария (`lease-recovery`, `managed-generations`, `agent-sigkill`), повторно проверив бинарник product-клиента, квитанцию активации и запись PostgreSQL на обеих нодах.

На машине подготовки релиза распакуйте артефакты только из доверенных успешных запусков CI проверяемых PR. Сопоставьте все три результата с фактическими байтами кандидата:

```bash
python3 scripts/quota_v2_release_candidate.py \
  --candidate ./agent-candidate \
  --node-revision "$REVIEWED_NODE_SHA" \
  --nexus-revision "$REVIEWED_NEXUS_SHA" \
  --evidence ./lease-recovery/installed-evidence.json \
             ./managed-generations/installed-evidence.json \
             ./agent-sigkill/installed-evidence.json
```

Проверка отклоняет заменённые файлы, чужие SHA, повтор одного сценария вместо трёх и несовпадение установленного product-бинарника с кандидатом. SHA-256 проверенных Xray также сохраняются для последующей квалификации dataplane. Сама утилита не удостоверяет происхождение скачанных артефактов и не выдаёт криптографическую подпись или полномочие на установку. Результат всегда содержит `productionActivationAuthorized=false`: это доказательство соответствия **стендовым** испытаниям, а не готовности штатного обновления/отката или production-активации. Утилита не запускается на рабочих VPS.
