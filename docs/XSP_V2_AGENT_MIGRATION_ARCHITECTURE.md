# XSP-v2 P0-D — Real Agent integration / Go 1.27 migration architecture

Status: **design gate only; no production activation**  
Nexus design base: `11d163c0788d953d3c4501b2dc3b1b56fe9b65fb`  
Verified Node artifact base: `bedbec74413a5ea86f69aca685f24bf028775a98` (Node PR #34 + hardening PR #35)

This document closes the architecture ambiguity before staged download/apply work begins. It does not install the Go 1.27 Agent, enable XSP-v2 in production, retire the existing control Agent, or turn `strict-pq` on.

## 1. What is actually deployed today

The root `XMesh-Node` Go module is Go 1.23. It is the edge router/data-path front end. It listens for client TCP/UDP traffic and forwards to Xray backends. **The root Go 1.23 router is not the control Agent.** It must not be treated as the component that P0-D migrates merely because both live on a Node host.

The currently deployed signed control/update plane is separate and remains authoritative until an explicit later cutover gate:

- `/usr/local/sbin/xmesh-node-control` from Nexus `deploy/node-control-agent.sh` polls signed control commands, reports Node/control health, enforces fixed actions and sends signed ACKs;
- `xmesh-node-control.service` + `xmesh-node-control.timer` schedule the signed control loop;
- `/usr/local/sbin/xmesh-update-agent` from Nexus `deploy/update-node-control-agent.sh` performs the existing fixed `update_agent` apply path;
- `xmesh-node-agent-upgrade.service` is the hardened root/systemd executor for that fixed updater;
- the updater also reconciles the XMesh-Node router checkout/container and the Xray/policy/GeoData/profile/TLS helpers. Those responsibilities are not implicitly transferred to the new Go Agent by this design gate;
- the Ed25519 enrollment identity under `/etc/xmesh-node-metrics` is existing production identity material and must not be silently regenerated by migration.

Xray remains the VPN data-plane. The root Go router remains a separately versioned edge-routing component. P0-D changes the control-plane Agent boundary, not the user VPN protocol and not the router solely to change its Go toolchain.

## 2. Existing Go 1.27 integration boundary to reuse

XMesh-Node already contains the side-by-side `agent/xspv2` Go 1.27.3 module introduced by Node PR #34 and fail-closed source-contract hardening from PR #35.

That module is the only approved starting point for the future production-capable XSP-v2 Agent. It already provides a production-style private state root and a thin bridge into the proven XSP-v2 cutover implementation. It must **reuse**, not copy, the existing strict transport / permit / signed ACK / dual-signed receipt / historical recovery state machine.

The migration must therefore converge on one state machine:

`Nexus immutable release identity -> fixed update_agent orchestration -> Go 1.27 Agent integration -> reused XSP-v2 strict transport + permit/ACK/receipt/recovery primitives`

Creating a second XSP-v2 protocol implementation inside Nexus shell scripts, the root router, or a new Go package is out of scope and forbidden.

## 3. Target responsibility split

| Responsibility | During migration | Target owner after later approved cutover |
| --- | --- | --- |
| Edge TCP/UDP routing and SNI/ALPN forwarding | root Go 1.23 router remains unchanged by this gate | independently versioned XMesh-Node router; Go version may change only in its own gate |
| Signed legacy control polling / fixed actions | current shell `xmesh-node-control` remains active by default | Go 1.27 Agent only after explicit cutover gate |
| Immutable release identity `{version, sourceRevision, artifactSha256}` | Nexus DB + signed poll/ACK contract from PR #90/#91/#93/#95 | unchanged contract consumed by Go 1.27 Agent |
| Strict XSP-v2 transport and authority binding | staging Go 1.27 `agent/xspv2` reuse only | Go 1.27 Agent, with `Address` separate from authenticated `ServerName` |
| Permit / ACK / receipt / recovery journal | proven XSP-v2 Go primitives; no parallel shell state machine | Go 1.27 Agent private state under `/var/lib/xmesh-agent/xsp-v2` |
| Artifact download / digest verification / atomic apply | **not implemented in this design gate** | next P0-D staged apply gate |
| Last-known-good rollback | current updater rollback remains for current components; Go Agent rollback contract defined below | staged apply gate must implement before activation |
| Xray reconciliation, policy guard, GeoData, profile/TLS helpers | existing shell/Python/systemd workers remain | separate responsibilities unless a later reviewed gate moves them |

## 4. Packaging and release contract

The supported future Agent artifact is the Linux binary built from XMesh-Node `agent/xspv2` with Go 1.27.3 or a later explicitly reviewed Go 1.27.x toolchain. A production migration release must be represented in Nexus by the already-existing immutable manifest identity:

`version + sourceRevision + artifactSha256`

Rules:

1. `sourceRevision` identifies the exact reviewed XMesh-Node source commit used to build the Agent artifact.
2. `artifactSha256` identifies the exact packaged Linux Agent bytes; it is never caller supplied at orchestration time.
3. The remote action remains exactly `update_agent`. No script, shell command, URL, URI or executable path is added to the command schema.
4. The apply implementation must consume only server-approved immutable release identity and a separately bounded artifact source defined by the next gate.
5. Building a new Agent version does not activate it. Production continues to run the current shell Agent unless an explicit non-default migration/cutover gate selects and successfully applies an approved release.

## 5. Install layout and process boundary

The Go 1.27 Agent must remain side-by-side until cutover is proven. The intended private state root is `/var/lib/xmesh-agent/xsp-v2` with mode `0700`, Agent ownership and no symlink components.

A future package/apply gate may introduce a dedicated binary and systemd unit, but it must not overwrite `/usr/local/sbin/xmesh-node-control` before all of the following are true:

- the exact approved artifact digest/revision has been verified locally;
- the new binary passes an offline/self-check before activation;
- durable XSP-v2 state is readable and monotonic;
- the previous known-good Agent binary/package is retained;
- systemd activation can be reverted without re-enrollment or key regeneration;
- Nexus has not yet accepted success merely because a process started.

`xmesh-node-agent-upgrade.service` remains the bounded executor for the existing fixed update path until the staged apply gate deliberately replaces or narrows it. The design does not create a second remotely callable updater.

## 6. Last-known-good rollback boundary

Before any future apply mutates the active Agent, the node must have a complete **last-known-good** tuple:

- active Agent version;
- exact source revision and artifact SHA-256 when the active Agent is manifest-bound;
- active executable/package reference;
- required systemd unit definition/version;
- durable Agent state root version;
- enrollment/key references that must survive rollback.

Rollback is local and bounded. It restores the previous Agent package/service state and reuses the same enrolled identity and durable security state. It must never roll security epochs/replay floors backwards, delete an ACK/receipt journal, generate replacement keys automatically, or reinterpret an older Agent as permission to use a weaker protocol.

A failed apply, failed self-check, failed authenticated startup, missing receipt, or failed post-start health proof is failure. Nexus must not mark the migration successful until the exact authenticated ACK/receipt requirements of the selected migration phase are satisfied.

## 7. Mixed-version compatibility matrix

There is **no silent downgrade** for a migrated operation.

| Nexus / command | Node control implementation | Required behavior |
| --- | --- | --- |
| legacy unbound command | current shell Agent | existing XMESH1/Ed25519 legacy behavior remains compatible until separately retired |
| legacy unbound command | future Go 1.27 Agent before cutover authorization | compatibility may be provided only through an explicit legacy mode; it must not be confused with XSP-v2 success |
| manifest-bound staged `update_agent` | current shell Agent from PR #95 | exact release identity poll/apply/ACK contract; no fabricated success |
| XSP-v2 migrated operation | Go 1.27 Agent with required keys/state | strict XSP-v2 path only |
| XSP-v2 migrated operation | old shell Agent or Go Agent missing required PQ/state support | fail closed; operation is unsupported |
| XSP-v2 migrated operation | peer offers XMESH1, Ed25519-only, X25519-only, TLS 1.2, insecure certificate validation or changed HTTP authority | fail closed; never retry through the weaker path |

A deployment may temporarily contain old and new peers, but protocol choice is attached to the operation/gate, not negotiated down from failure. An XSP-v2 operation that cannot meet its minimum suite remains failed/pending; it is never converted into a successful legacy operation.

## 8. Transport authority invariant

The proven Node rule remains binding:

- `Address` is the direct TCP connect target and may be an internal alias/IP;
- `ServerName` is the authenticated authority for TLS SNI, certificate hostname verification and HTTP `Host`;
- redirects, proxies, alternate virtual hosts, TLS downgrade and XMESH1 fallback cannot change that authority after or instead of strict authentication.

The Go 1.27 Agent must call the existing strict XSP-v2 transport bridge. It must not recreate transport using a default `http.Client` or a second TLS configuration.

## 9. Activation sequence for later gates

This design authorizes only the following future order:

1. staged download into a private non-active location;
2. verify exact immutable release identity and artifact digest;
3. run offline/self-check against the intended state root;
4. snapshot the last-known-good package/service boundary without rolling back security state;
5. atomically switch the Agent executable/service;
6. prove authenticated startup and exact command/ACK identity;
7. for XSP-v2 migrated operations, prove the required permit/ACK/receipt/recovery path;
8. only then report success;
9. on failure, restore the previous Agent package/service while preserving monotonic security state and report failure.

Durable-state layout, actual downloader, atomic apply mechanics and rollback implementation belong to the next P0-D gates and require their own positive/negative/restart tests.

## 10. Non-goals / production guardrails

This design gate deliberately does **not**:

- install or enable the Go 1.27 Agent on production nodes;
- alter the root Go 1.23 router or its Compose service;
- remove the shell control Agent, updater, metrics, Xray sync, policy, GeoData, profile or TLS helpers;
- add an arbitrary remote command, script or caller-selected artifact location;
- change enrollment keys or retire old keys;
- activate XSP-v2 production ingress;
- authorize production rollout.

`strict-pq` remains OFF. Production behavior remains on the current deployed control path until later P0-D/P0-E and release gates explicitly authorize cutover.
