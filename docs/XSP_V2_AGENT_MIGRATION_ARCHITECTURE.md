# XSP-v2 P0-D — Real Agent integration / Go 1.27 migration architecture

Status: **staging implementation boundary; no production activation**  
Verified Nexus base before this contract gate: `bafb66089b93591eda6efed05c4fcb20be2b4712`  
Verified Node implementation checkpoint: `5e8ee562915a570eb49ed46d59d723f233f3cc68` (Node PR #37)

This document records the production-capable Agent migration architecture after staged package apply/rollback and disposable real-Agent E2E have been implemented. It does not install or activate strict XSP-v2 in production, retire the shell control Agent, or turn `strict-pq` on.

## 1. Component ownership remains explicit

The root XMesh-Node Go 1.23 module remains the edge router/data-path front end. It is **not** the signed control Agent and is not migrated merely because it lives on the same host.

The deployed signed control/update plane remains authoritative until a later explicit production cutover:

- `/usr/local/sbin/xmesh-node-control` from Nexus `deploy/node-control-agent.sh` polls signed commands and sends signed ACKs;
- `/usr/local/sbin/xmesh-update-agent` plus `xmesh-node-agent-upgrade.service` remains the fixed `update_agent` executor;
- the remote action surface is not broadened;
- existing production enrollment material is never silently regenerated by migration.

Xray remains the VPN data-plane.

## 2. Approved Go 1.27 Agent boundary

XMesh-Node `agent/xspv2` is the **only approved starting point for the production-capable XSP-v2 Agent**. At exact Node merge `5e8ee562915a570eb49ed46d59d723f233f3cc68` it is a Go 1.27.3 side-by-side module that reuses `security/xspv2/poc-go` rather than copying protocol or security state machines.

The migration converges on one chain:

`Nexus immutable release identity -> fixed update_agent -> staged verified package -> agent/xspv2 -> reused keyring + cutover + strict transport`

No second command queue, shell crypto implementation, router-side cutover state machine, or generic remote executable surface is allowed.

## 3. Completed package/service lifecycle

Nexus PR #101 implements the staged download / verify / apply / rollback boundary. PR #103 proves disposable real Nexus↔Node success, lost-response recovery, restart/idempotent apply and deterministic rollback with real pinned Go 1.27.3 Agent artifacts.

The package side is content-addressed and manifest-bound:

1. caller selects only an approved release version;
2. Nexus resolves immutable `sourceRevision` + `artifactSha256` server-side;
3. bytes come only from the bounded server/operator-controlled release source;
4. artifact SHA-256 and embedded version/source revision are verified before activation;
5. an exact last-known-good package/service tuple is retained;
6. activation uses a bounded switch rather than overwriting unverified active bytes;
7. failure restores package/service state without rewinding security state;
8. exact signed ACK identity remains required for Nexus success.

The root Go 1.23 router image stays outside this package boundary.

## 4. Real-Agent durable security-state layout

Node PR #37 separates signed cutover journals from encrypted key state:

```text
/var/lib/xmesh-agent/xsp-v2/
├── cutover/
│   ├── xsp2-verified-permit.json
│   ├── xsp2-applied-ack.json
│   └── xsp2-verified-commit-receipt.json
└── keys/
    ├── node-request.master
    ├── node-request.vault
    ├── node-request.vault.min-epoch
    ├── node-request.vault.next
    └── node-request.vault.previous
```

`state.Prepare` creates/hardens only the private `cutover/` and `keys/` directories. It must not initialize, reset, replace, retire or regenerate enrollment identities.

The signed permit/ACK/receipt files remain owned by the reused `cutover` implementation, preserving exact-byte binding, immutable retry, atomic rename, file `fsync`, directory `fsync`, corruption rejection and historical recovery semantics.

The encrypted identity/floor/snapshots remain owned by the reused `keyring` implementation.

## 5. Monotonic applied-state attestation

Before a migrated signed ACK exchange or historical receipt recovery can perform network I/O, `agent/xspv2/runtime` requires the real-Agent state wrapper to call `keyring.AttestAppliedRotation`.

That attestation proves under the wrapping-key lock:

- persisted minimum epoch equals exact expected `toEpoch`;
- active encrypted vault equals the prepared candidate;
- `.next` authenticates the exact candidate identity;
- `.previous` authenticates and retains the exact old identity;
- Node ID, purpose, epoch and old/new key IDs match the signed permit.

The runtime additionally requires the resulting active public identity to match the authenticated pending signer byte-for-byte and requires `minimumEpoch == permit.ToEpoch`.

This means package rollback **must never lower the security epoch/replay floor**, restore an old active identity under a newer floor, delete the retained old key snapshot, or regenerate keys. Restoring an old vault, lowering/corrupting the floor, deleting `.previous`, substituting public keys, or presenting stale/mismatched layout fails closed before transport.

There is no second generalized replay database in the wrapper: exact operation replay identity remains in the proven immutable cutover journals, while the key epoch floor prevents an old operation/package from being reinterpreted as current security state.

## 6. Restart and rollback boundary

Node tests prove that after an applied rotation, re-running `state.Prepare` preserves the exact master, active vault, floor, `.previous` and `.next` bytes. This models Agent/process restart and filesystem reuse without auto-reenrollment.

Last-known-good package rollback is deliberately orthogonal. It may restore an earlier verified binary/service tuple, but the same `/var/lib/xmesh-agent/xsp-v2` security state remains authoritative. Package rollback cannot erase or lower security evidence.

Old keys remain retained until a separately authorized retirement workflow exists.

## 7. Authenticated transport authority

The proven authority split remains binding:

- `Address` is the direct TCP destination and may be an IP/internal alias;
- `ServerName` is the authenticated TLS identity;
- TLS SNI and certificate hostname verification use `ServerName`;
- **HTTP `Host` equals the authenticated `ServerName`**;
- the migrated client has no inherited proxy;
- redirects are rejected;
- alternate virtual hosts, TLS downgrade, and legacy/XMESH1 retry cannot replace the authority after an operation enters the XSP-v2 path.

The Agent uses the reused strict cutover transport (`DialStrictMutual`) rather than a default HTTP client or independent TLS stack.

## 8. Mixed-version rules

| Operation | Node capability | Required behavior |
| --- | --- | --- |
| legacy unbound `update_agent` | current shell Agent | legacy behavior remains compatible and distinct |
| manifest-bound staged Agent update | current staged lifecycle | exact immutable release identity; no fabricated success |
| XSP-v2 migrated operation | Go 1.27 Agent + exact durable applied state | strict path only |
| XSP-v2 migrated operation | missing/corrupt/stale key state | fail closed before network |
| XSP-v2 migrated operation | wrong authority/PQ support/receipt | fail closed; no legacy fallback |

Protocol choice is attached to the operation/gate. Failure never renegotiates a migrated operation into XMESH1, Ed25519-only, X25519-only, TLS 1.2, insecure verification, redirected authority, or proxy-selected authority.

## 9. P0-D acceptance position

With PR #101, PR #103 and Node PR #37, the implemented staging architecture now covers:

- immutable release identity and fixed orchestration;
- signed release identity through poll/apply/ACK;
- staged artifact verification and atomic package/service rollback;
- disposable real Agent success/retry/lost-response/restart/rollback;
- durable real-Agent key/journal layout and monotonic applied-state attestation;
- authenticated `Address` / `ServerName` / HTTP authority binding.

Nexus still must machine-bind these Node invariants to the exact merged Node SHA and pass exact-head + fixed-head merge + post-merge CI before P0-D overall may be marked complete. That is the purpose of the current Nexus contract gate.

## 10. Production guardrails

This gate does **not**:

- enable the Go 1.27 Agent by default on production nodes;
- alter the root Go 1.23 router deployment;
- remove the shell control Agent/updater;
- add an arbitrary remote command, script, URL or executable path;
- retire old keys;
- activate production XSP-v2 ingress;
- authorize production rollout.

`strict-pq` remains OFF. P0-E and an explicit production release/canary plan remain separate required gates.
