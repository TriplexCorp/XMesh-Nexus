# XRAY STUDIO: проверка через установленный Xray-core

## Реальная проверка
Кнопка **Проверить** обращается к защищённому `POST /api/v1/core/validate` с телом `{"config":"{...}"}`.
Backend проверяет синтаксис JSON и запускает **установленный в панели** бинарник `<core-root>/current/xray run -test -format=json -config=stdin:`.
Конфигурация поступает по stdin, не сохраняется на диск, не запускает сетевой сервер. Ограничения: 512 КиБ исходных данных и 8 секунд, завершение дочернего процесса при отмене; доступ только для авторизованного пользователя с правом изменения.

Ответ содержит `valid`, `engine`, `stdout`, `stderr` и `message`. Только `valid: true` от данного endpoint является подтверждением проверки **ядром**, а не эвристическим анализатором.

## Диагностика в редакторе
- Синтаксис JSON: местоположение вычисляется из ошибки JS JSON.parse, если движок указал строку или позицию.
- Предварительный анализ XrayJsonIntelligence: выделяет ошибки в строках по своей карте токенов. Это не сообщения Xray-core и не основание считать профиль принятым ядром.
- Xray-core: отдаёт текст ошибки. Подчёркивание строки делается **только если Xray явно указал номер строки**. Сообщения Xray о семантических проблемах часто не содержат координат, поэтому их надо показывать без выдуманного местоположения.
- При изменении документа результаты прежнего запуска ядра сбрасываются; повторная проверка выполняется вручную, а не при каждом нажатии клавиши.

## Ограничения
`xray run -test` проверяет загрузку конфигурации конкретным бинарником панели, но не проверяет фактический трафик, доступность внешних серверов, ключи у клиентов или runtime-файлы удалённых узлов. Данные и файлы, которые имеются только на удалённых нодах (сертификаты, geodata и т. п.), могут приводить к отклонению локального теста.

Использовать для конфигураций от полноценных авторизованных редакторов. Не открывать endpoint анонимным пользователям: это реальный процесс Xray, хотя и не запускающий сетевой сервер. Более строгая изоляция потребует отдельного sandbox/worker.

## Выявленные проблемы при сравнении с документацией
1. Прежний шаблон VLESS создавал `settings.clients: []`. У VLESS inbound актуально `settings.users: []`. Исправлено в новых профилях.
2. Конструктор переключает `protocol` между VLESS, VMess, Trojan, Shadowsocks, но не преобразует все протокольные поля. Это может создавать некорректный config. Необходимо сделать протокол-специфические формы и безопасный переход.
3. Начальный серверный шаблон VLESS имеет `security: none`, `decryption: none`, `listen: 0.0.0.0`. Для публичных подключений этого недостаточно — следует требовать транспортную защиту или VLESS Encryption, либо подтверждать использование доверенной частной сети.
4. Доступные поля Reality, XHTTP, TLS, routing, DNS и остальные должны зависеть от реальной версии установленного Xray: документация отслеживает актуальную версию, которая может не совпадать с версией бинарника панели.
5. Для профилей, исполняемых на удалённых узлах, необходима проверка с использованием соответствующего бинарника/файлов узла (позже — через защищённый агент), а не только панели.
