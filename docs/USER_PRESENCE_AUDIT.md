# Аудит статуса пользователей: Xray → нода → Rust → UI

Дата: 2026-10-24. Область проверки: XMesh Nexus + TriplexCorp/XMesh-Node.

## Что означает «Онлайн»

Сейчас это **наличие подтверждённой передачи байтов Xray за последние 45 секунд**, а НЕ наличие открытого TCP/UDP-соединения. Индикатор не может моментально обнаружить физическое отключение клиента по одним кумулятивным счётчикам. Наличие другого устройства, фоновых запросов и keepalive продлевает активность.

| Участок | Механизм |
|---|---|
| Xray → привилегированный policy guard | `xmesh-node-user-meter.timer`, примерно раз в 10 с |
| Узловой metrics-agent → Rust | `xmesh-node-metrics.timer`, через 5 с после предыдущего выполнения |
| Rust → UI «Пользователи» | защищённый `GET /api/v1/users/presence`, каждые 10 с |
| TTL подтверждённой активности | 45 с; отображение может измениться позже следующей перерисовки |

## Найденные и исправленные ошибки

1. Старая страница использовала TTL 300 000 мс (5 мин), обновляя всё состояние панели раз в 30 с. Теперь TTL согласован между Rust/JS/узловым подсчётом, а UI запрашивает только `id` и `onlineAt` без секретов подписок.
2. Metrics-agent выдавал время отправки за время исходного Xray snapshot. Теперь передаётся проверенное `sampledAtMs` из защищённого root-only снимка. Обновить скрипт необходимо **на каждой ноде**.
3. Rust отдельно обновлял `onlineAt` и кумулятивные счётчики, допуская гонку и ложное возобновление активности после старого/сброшенного снимка. Теперь запись производится в SQL-транзакции с `pg_advisory_xact_lock(node_id)`, проверкой монотонности обоих направлений и свежести/порядка исходных samples.
4. В открытой карточке пользователя точка активности не пересчитывалась. Теперь она обновляется вместе со списком.
5. Метрика `online_clients` на ноде отдельно использовала 120 с; синхронизировано окно в 45 с.

## Ключевые проверки на ноде

```bash
systemctl list-timers 'xmesh-node-*' --no-pager
systemctl status xmesh-node-user-meter.timer xmesh-node-metrics.timer --no-pager
journalctl -u xmesh-node-user-meter.service --since '-15 minutes' --no-pager
journalctl -u xmesh-node-metrics.service --since '-15 minutes' --no-pager
sudo stat /run/xmesh-node-user-metrics.json
sudo python3 - <<'PY'
import json,os
p='/var/lib/xmesh-xray-sync/policy-usage.json'
if os.path.exists(p):
    with open(p,encoding='utf-8') as f:data=json.load(f)
    print('Journal bytes:',os.path.getsize(p))
    print('Retained users:',len(data.get('users',{})))
    print('Retained inbound records:',len(data.get('inbounds',{})))
PY
docker stats --no-stream
```

Данные `policy-usage.json` являются источником автономного учёта. **Не удаляйте и не обнуляйте этот файл для очистки памяти**: это может нарушить лимиты и учёт трафика.

## Go и память

Сам Go-компонент XMesh-Node обслуживает TCP/UDP маршрутизацию и отдельные heartbeat, но **не вычисляет пользовательский онлайн**. Его TCP-соединения ограничены `MaxTCPConnections`, UDP-сессии — `MaxUDPSessions`; UDP idle cleanup запускается каждые 30 секунд. В процессе работы память Go может оставаться зарезервированной для повторного использования после GC — это само по себе не утечка.

Реальный ресурсный риск в отдельном Python policy guard: журнал `policy-usage.json` сохраняет записи когда-либо увиденных пользователей/inbound без механизма подтверждённого удаления. При большом обороте пользователей количество записей способно постепенно превысить проверяемый предел 4096, после чего часть узловой телеметрии станет недоступной. Автоматически удалять эти записи **нельзя без подтверждённого учёта в Control Plane**. Это отдельная оставшаяся архитектурная задача, не решаемая настройкой Go GC.

## Проверки и ограничения

- Добавлен статический регрессионный тест `node scripts/check-user-presence.js` в CI.
- В подписанный интеграционный тест телеметрии добавлена проверка устаревшего снимка и неизменности последней активности/счётчиков.
- Не проводилось измерение RSS/heap на живых нодах и не выполнялся реальный `cargo test` в среде разработки.
- На время обновления панели раньше скрипта ноды возможны устаревшие события; сначала разворачивать backend, затем обновить node-metrics-agent на всех нодах.
- Для действительно точного статуса подключений требуется отдельная метрика активных сессий Xray. Кумулятивный StatsService не позволяет установить факт разрыва соединения мгновенно.
