# XMesh Nexus Design System v3

Status: **authoritative panel design and composition contract**.

The panel has **one presentation entrypoint**: `nexus-ui-v3.css`.
The goal is simple: **the panel must be designed as a system, not repaired page by page.**

## Active architecture

The browser loads one content-addressed panel presentation entrypoint:
`frontend/styles/system/nexus-ui-v3.css`. It imports, in order:

1. `nexus-v3-foundation.css` — tokens, density, radii, Classic / Glass / Raised;
2. `nexus-v3-components.css` — shared surfaces, controls and dialog materials;
3. `nexus-v3-layout.css` — page-agnostic shell, workspace and responsive primitives;
4. scoped CSS files from `styles/features/` — feature-specific geometry, including Settings and Nodes.

The public subscription portal uses a separate stylesheet. The authenticated panel does
**not** load the retired legacy stylesheet, DOM-inference builder or fourth workspaces module.
See `scripts/check-ui-system.js` for the enforced asset graph. Cache keys are generated by
`node scripts/update-ui-cache.cjs`; do not invent query-string versions manually.

## Ownership model

### Foundation owns

- surface material and Appearance modes;
- global radius and border behavior;
- density scale;
- spacing/control tokens;
- compatibility token aliases where existing renderers still consume them.

### Components own

- `.card` and shared material surfaces;
- buttons, inputs, selects and segmented controls;
- table visual language;
- dialog material;
- focus / hover / selected states;
- nested-surface depth isolation.

### Layout owns

Only page-agnostic geometry:

- application shell and `.wrap`;
- generic `.view` flow;
- toolbar geometry;
- metric grids;
- low-count collections;
- empty-state sizing;
- tables and generic sparse states;
- editor/canvas exceptions;
- modal viewport safety;
- global responsive shell behavior.

`nexus-v3-layout.css` must **not** contain `.appearance-layout`, `.nodes-page` or any other complex page-specific workspace selector.

### Feature CSS owns

Only geometry or typography specific to a page, feature, editor or dialog. Settings and Nodes own their composition in their scoped feature styles, as do XRAY STUDIO, TLS/Reality editors, routing, diagnostics, user creation and subscription tooling.

Feature CSS must not implement its own Classic / Glass / Raised material, global button system, global card system, `.wrap`, `.view` or application-shell policy.

## Explicit runtime semantics

Renderers declare `data-workspace`, `data-ui-surface`, `data-ui-collection`
and toolbar/metric roles in their own markup. `frontend/js/core/app.js` owns route
rendering and explicit workspace metadata. There is no runtime UI builder.

Do not bring back mutation-based DOM classification, position arbitrary panels
from JavaScript measurements, or infer a page layout from incidental descendants.
Feature markup owns structure; system and scoped feature styles own presentation.

## Surface roles

Use these shared roles:

| Role | Purpose |
| --- | --- |
| `panel` | top-level card/workspace surface |
| `dialog` | modal shell |
| `section` | grouped content inside a surface |
| `metric` | KPI/stat tile |
| `item` | list/selectable item |
| `floating` | popover/dropdown |

Preferred markup:

```html
<section data-ui-surface="section">...</section>
```

Feature renderers declare roles explicitly; their materials come from the shared system.

## Width contract

The application shell's `.wrap` uses available width, while the route `.view`
applies explicit `data-workspace` sizing and the Appearance content-width limit.
This setting does not command each inner card or control to stretch.

- Data tables/lists use their assigned workspace responsively.
- Scoped features may set intentional, readable track caps. Nodes currently
  uses Compact 40rem, Standard 68rem and Spacious 76rem, left-aligned.
- Editors/canvases can use the assigned width when productive.
- Controls, copy rails and KPIs use proportional, readable internal tracks.

Do not globally narrow the shell to solve a feature's ultrawide geometry.

## Spatial contract

**Content-driven height is the default**.

A surface must not be substantially taller or wider than its meaningful content unless the extra space has a product purpose such as an editor, chart canvas, preview, drop zone or explicit empty state.

Avoid:

- decorative `min-height`;
- forced equal-height generic cards without a product reason (Nodes fleet deliberately aligns rows);
- `flex-grow` used only to fill the viewport;
- oversized padding that simulates importance;
- controls stretched simply because a track is wide;
- tiny information stranded inside a huge card;
- fixed-width KPI bottlenecks on a wide operational surface;
- hidden implicit grid columns;
- `display: contents` used to defeat meaningful workspace wrappers;
- separate full-width rows for tiny metadata that belongs in a toolbar;
- empty modal bodies/footers inherited from a larger editor layout.

**Low-count states recompose.** One or two objects should use deliberate, density-specific track sizes instead of preserving fleet-scale columns.

**Do not fill voids with fake UI.** Fix the geometry that created the void.

## Retired implementations

The following files and their behaviors have been removed and must not be restored:

- `frontend/styles/legacy/styles.css`;
- `frontend/js/core/ui-builder.js`;
- `frontend/styles/system/nexus-v3-workspaces.css`;
- `scripts/ci/stage-frontend-compat.sh`.

The modern panel imports scoped CSS through its single presentation entrypoint.
Do not add a fallback layer, synthetic compatibility files, DOM-inferred layouts
or a second global style authority. `scripts/check-ui-system.js` enforces their absence.

## Material contract

Appearance remains authoritative:

- `data-surface="solid"` → Classic;
- `data-surface="glass"` → Glass;
- `data-surface="raised"` → Raised.

Glass must use real transparency/backdrop blur unless the OS requests reduced transparency.

Raised is a neutral depth hierarchy, not an accent-tinted theme. Accent belongs to selection, focus, status and primary action.

Raised cards must use a low-contrast solid surface and one restrained elevation shadow. Do not paint full-card shine gradients or stack decorative inner shadows on nested sections and controls. The same depth tokens apply across all sections, including Settings.

Nested modal sections do not stack outer shadows or backdrop filters. A dialog has one primary material shell.

Separators are structural and remain quieter than surface borders, including Strong border mode.

## Interaction contract

Bloom is not an interaction primitive.

Surfaces/cards must not acquire neon glow or floating lift on hover. Shared interactive controls may use the existing subtle press/hover motion. Selected state must remain more obvious than hover. Keyboard focus uses the shared focus token.

Composite controls have one material shell; inner native inputs remain transparent/borderless.

## Core composition rules

### Settings

Settings uses two real workspace columns on wide desktop: approximately 54/46 rather than six independently positioned cards.

Requirements:

- `.appearance-column` remains a real grid wrapper;
- cards are content-height, never forced equal-height;
- old explicit `grid-area` placement is neutralized;
- title/description anatomy stays quiet and consistent;
- controls use a readable right rail instead of a half-screen stretch;
- palette presets use a stable full-card grid;
- font selection is a structured chooser, not a wrapped sentence;
- custom-palette and range controls reflow before clipping;
- responsive behavior is based on actual workspace width through container queries.

Decorative pseudo-icons must not be generated merely to make Settings look “premium”. Hierarchy comes from typography, spacing, material and grouping.

### Nodes

The active owner is `frontend/styles/features/nodes/nodes.css`; `nodesP()` in
`frontend/js/core/app.js` renders the anatomy. The three-system-module asset
contract is enforced by `scripts/check-ui-system.js`.

- Nodes tracks are anchored to the left workspace edge and capped by density: Compact 40rem, Standard 68rem, Spacious 76rem.
  Cards and their action buttons stop stretching across ultrawide low-count fleets;
  narrower workspaces still shrink the tracks to fit. Global radius settings remain authoritative.
- Compact is the square-card experiment: summary above telemetry, a separating line,
  and three horizontal KPI tiles at readable card widths. Its proportions follow
  content, with no forced aspect ratio or clipped actions. Four action columns fit
  from a 36rem content width; narrower cards retain the two-column fallback.
- The header groups flag/name/endpoint/provider on the left and runtime badges on the right.
- `.node-body` is a real grid: summary 40%, telemetry 60% once the card has room.
- Users and XRAY STUDIO are adjacent summary columns with a vertical divider.
- TLS retains its shield during runtime updates; GeoData retains its status dot.
- Three equal-height KPI tiles share one row above the full telemetry speed rail.
- Actions use four equal columns, four equal columns, then full-width Create Host.
  Only narrow cards reflow to two columns.
- Card depth comes from `--nx-panel-shadow`; accent outer bloom is forbidden.
- Compact / Standard / Spacious change actual fleet track geometry.
- Equal fractional fleet rows and stretched cards keep every rendered card at
  the same content-driven height, across rows and runtime states. The middle
  body absorbs available space, keeping telemetry and actions at the bottom;
  no fixed card height or runtime DOM measurement is used.
- Container queries use card width for anatomy and workspace width for fleet density.
- Icons come from the shared `ic()` SVG renderer.

### User Details

`workspace-dialog-contract.css` owns final dialog geometry; `user-details.css`
owns feature content. The desktop height budget uses the viewport minus its safe margin, so content
can grow beyond the former 54rem cap when the screen has room. Header, usage band, task tabs, shared Save action and footer stay in flow without shrinking.
Settings, Access & subscription, Traffic and Devices use one intrinsic panel grid.
Inactive panels remain mounted with `inert` and `aria-hidden`, preserving the
shared settings/access draft and dialog geometry. Arrow keys, Home and End move
between tabs. Validation reveals the affected panel; errors stay outside panels. `.user-canvas-grid` is the single scroll owner
with a stable scrollbar gutter. `userDrawer()` resets that owner's scroll
position after mounting, including when another user replaces an open dialog.

Browser acceptance lives in `scripts/test-ui-browser.cjs`: real DOM rectangles,
semantic icons after runtime refresh, neutral computed shadow, 4 + 4 + 1 actions,
viewport-safe height without the former 54rem cap, pane baselines, and reopening after a real scroll.
Artifacts include `nodes-{width}x{height}.png` and
`user-details-{width}x{height}.png` at 1920×1080, 2560×1440 and 3440×1440.

#### User creation: resilient metadata layout

The create-user “Дополнительно” section is a named CSS **size container**
(`nx-user-extra`) whose layout follows its *actual available inline size*, not
the browser viewport. This protects normal screens, browser zoom and nested
dialog widths alike. Use a single metadata column on narrow surfaces, two
balanced columns with full-width Squads/Notes at medium widths, and only
enable four metadata columns when the section is genuinely wide enough.

Every grid child must have `min-width:0`; field labels must wrap naturally.
Squad chips wrap inside a bounded, **vertical-only** scroll area. Notes must
wrap and allow vertical resizing without horizontal scrolling. On-hold remains
a native accessible checkbox/switch in a full-width field row. Do not impose
identical fixed heights or wide minimum widths on independent fields.

This is feature-scoped composition using existing Nexus material tokens;
never introduce a separate field theme. The scrollable dialog body and fixed
footer remain the existing single-scroll-owner contract. Browser regression
must exercise narrow, medium and wide viewports, many squad chips, long
notes and on-hold interaction.

#### User Details visual continuity

User Details is an **existing Nexus workspace**, not a separate design product.
Do not implement generated neon/cyber mockups as a new CSS material or overlay.
All four tabs must inherit Classic, Glass, Raised, density, radius, borders,
accent, motion and focus from the global system. Feature CSS may improve layout
and content hierarchy, but must not add new glow, gradient frames, fake KPI
charts, decorative empty tiles or double-bordered panels.

Reuse the existing `ic()` SVG set for semantic section labels, dates and
actions. Keep the Xray usage donut and per-server breakdown tied to actual
authenticated user-counter data. A calendar may identify the timestamp of the
latest confirmed sample, but **never imply historical daily values** without a
time-series API. One user-level draft and Save action, inert inactive tabs,
one scroll owner, viewer masking and all device controls must be preserved.

Review every user-tab screenshot alongside surrounding Nexus pages in Classic,
Glass, Raised and both themes; adjust feature spacing, not global palette,
shadows or action-button anatomy.

### Devices and factual activity

The Devices and Activity dialog is **content-sized**. A fixed-position native
`dialog` inherits `inset:0` from Nexus; using `height:auto` here stretches
the outer frame to the viewport. Keep both `height` and `block-size` explicitly
`fit-content`, a viewport maximum, and **one** scroll owner on the body.
Never add a fixed/minimum height to fill space beneath two device rows.

Client-side activity **is not an anti-sharing verdict**. Traffic volume,
switching Xray servers, installing the app on multiple devices and growth in
registered HWIDs are observations, not proof that a subscription was shared.
Do not turn them into a synthetic 0–100 suspicion score, heat badge, automatic
warning banner or implied ban. Only display measured Xray traffic, distinct
nodes and registered-device timestamps; show unavailable history as unknown,
not zero. Enforcement of HWID limits belongs to the backend.

The Users directory shows a quiet Activity entry point; opening it fetches
history on demand rather than requesting seven-day samples for every table
row. The native dialog and embedded User Details surface share one feature
implementation and the global Classic / Glass / Raised, radius, density,
motion and focus contracts. Browser coverage must assert the content-height
boundary and the absence of speculative risk controls.

### Tables / Users / Squads / Hosts

Short tables are short surfaces. They do not reserve fleet-scale height. Empty page background below real content is preferable to artificial stretching.

Large data sets may use more horizontal space, but form controls and text still need deliberate reading widths.

Host editor markup and Node → Host country/remark presets belong to
`frontend/js/features/hosts/host-editor.js`. Its classic-script factory receives
live profile/node getters, profile/inbound lookup and the existing field/icon/
escaping helpers plus the country catalog. It owns no DB copy or route state.
`app.js` supplies the adapter and retains live preview, validation, X25519,
CRUD event dispatch and submit ownership. The feature owns accessible Host task
tabs: Connection (endpoint and node assignment), Client settings, and Preview.
All fields remain in one form; inactive tasks are inert and share one intrinsic
CSS grid frame so switching does not move the dialog or footer. Invalid controls
reveal their task before browser focus. The module does not define styles or a
second control/material system.

#### Squads directory

The Squad directory uses responsive content-height cards rather than a
stretched table. Cards retain Nexus materials, tokens, controls, icon renderer,
inbound chips and the existing Squad CRUD/editor. No per-squad device quota is
invented. Summary counts derive only from existing user membership and enabled
Host/Node relationships.

The 24-hour sparkline and volume come exclusively from
`GET /api/v1/squads/traffic/24h`, which aggregates `source_type='user'`
signed `verified_traffic_deltas` for **current** Squad membership, in
one-hour buckets. Never use node-network RX/TX as user consumption, fabricate
missing hourly samples, infer deltas from lifetime counters, or sum inbound and
user metric families. Sparse/empty data gets a truthful empty state, not a
fake curve. A user assigned to multiple Squads appears in each Squad; these
card totals are not additive for system billing. Latest activity reflects the
last verified sample, not an unverified live connection.

Do not create a new standalone card theme: use `--nx-panel-bg`,
`--nx-border-strong`, `--nx-card-radius`, `--nx-panel-shadow` and
the shared `ic()` icon set. Maintain keyboard-accessible editor and
Delete actions and verify 1920/1366/mobile viewport geometry in Chromium.

#### Squad editor

Squad create/edit stays a single native Nexus dialog (not an independent visual
theme). Its two-column editor preserves the actual `{name, desc, inb}`
CRUD contract and live impact preview, while using shared `ic()` symbols for
semantic titles, metrics, hosts and nodes. Keep the information density compact:
no oversized decorative tiles, forced equal heights or nested inbound scrollbars.

An optional **Xray profile** filter intersects with free-text search. It only
changes the visibility of inbound rows; it must never clear hidden selections,
alter the persisted inbound tags or silently restrict the global **Clear**
action. 'Select all' applies only to currently visible, present inbound rows.
Retain warnings for missing inbound/hosts/nodes and preserve functional labels,
accessible native selects, global Classic / Glass / Raised materials, and RU/EN
copy. Browser checks exercise profile filtering and no-scroll geometry on
1920, 1366 and mobile viewports.

The **Impact on subscriptions** preview follows a *summary-first* rule: show
only the four genuine counters (inbound, matching enabled hosts, associated
nodes and affected users) plus safety warnings by default. Do **not** dump
usernames or host tiles into the editor's initial viewport. Optional
`<details>` disclosure provides the relationship listings on demand, capped
for rendering performance; preserve the open state when inbound selection
recalculates the preview. Warning states must stay visible even when disclosure
is collapsed. Native HTML disclosure semantics, keyboard focus and existing
Nexus Classic/Glass/Raised tokens apply. Do not change membership or
persisted Squad data to achieve visual compactness.

### Settings center: six coherent workspaces

- The Settings rail contains **six** substantial pages, not a category per
  minor preference: `#set/general` (Panel: brand, behavior, integrations,
  notifications), `#set/appearance` (Appearance: colors, composition,
  typography, effects), `#set/system` (System & traffic: Xray, panel updates,
  LTE/CDN quotas), `#set/security` (Security Center), `#set/admins` (owner-only
  staff management), and `#set/data` (safe data and theme exports). `#set`
  opens Panel. These routes preserve browser Back/Forward and page reloads.
- Old saved URLs remain functional aliases with no duplicate forms:
  `#set/colors`, `#set/layout`, `#set/typography` open Appearance;
  `#set/integrations` opens Panel; `#set/traffic` opens System & traffic.
  Direct `#security` and `#admins` are still redirected to Settings.
- The global System rail contains **Settings only**. The real Security Center
  (MFA, sessions, audit and policy) and Administrators CRUD editor mount inside
  the Settings navigation without duplicate forms or alternate API handlers.
  Non-owners never see Administrators and are prevented from opening its deep
  link. Subscription Studio remains a separate functional workbench.
- Each workspace mounts **all existing cards belonging to its related feature
  groups**, and no unrelated cards. A pair of independent column stacks keeps
  short cards compact even beside long font or palette editors. The existing
  save handlers, IDs and authorization checks remain authoritative; no parallel
  forms or blank placeholder surfaces are introduced.
- Appearance choices save with the existing browser-local behavior; brand
  fields save through their existing form; webhook toggles persist immediately.
  Xray-core and panel-update operations retain their authenticated backend
  handlers. Fetch core/update metadata only while the System subpage is open.
- Keep existing field IDs, card identifiers, `data-ui` contracts and focus
  semantics intact. Deep links from the version rail and update actions must
  target the System subpage; destructive actions remain separately authorized.
- **Composition and empty-space budget:** Settings is left-aligned and fills
  the available dashboard workspace rather than being centered within a 96rem
  cap or restricting single-card pages to 54rem. The secondary navigation has
  compact, single-line rows; explanations live in the active page heading.
  Existing cards and controls use the shared density/layout tokens. Two-card
  pages collapse naturally on narrow viewports. Empty cards, fabricated metrics
  and oversized spacer blocks are forbidden.
- The shell and cards inherit `nexus-v3` material, density and spacing tokens.
  Secondary navigation must remain usable on narrow/mobile viewports and must
  not create horizontal document overflow.

### Dedicated CDN inbound traffic quota (stage 1)

- Settings → **Лимиты CDN** controls one shared pool of inbound tags.
  Any tag added to that group is metered across every node that runs the
  inbound. All unselected inbounds remain outside the CDN quota.
- Each user/template can specify `cdnLimitGb` (GiB, zero = unlimited) in
  addition to the existing global account `limit`. The ordinary unlimited
  user plan remains unaffected by exhausting their CDN pool.
- The panel derives `cdnUsedBytes` from verified, monotonic Xray stats in
  `user_inbound_traffic_totals`. Do not accept client-supplied usage or
  derive per-user quotas from node NIC totals, inbound aggregate statistics,
  or feed download counts. Counter resets retain their existing baselines.
- Once a user's CDN pool is exhausted, signed desired-config provisioning
  excludes that user's client from **only the chosen CDN inbounds**, leaving
  the original UUID and other authorized inbounds unchanged. Existing
  `user.limit` and expiry constraints still apply independently.
- **Enforcement limitation:** this stage uses normal node reconciliation;
  it does not promise instantaneous cutoff of live sessions and is not an
  offline-enforced hard quota. Production hard-cutoff requires a separate
  signed Agent policy extension with local inbound counters, reconnect
  denial, shared budget allocation, restart handling and fail-closed
  telemetry safeguards. Do not describe it as an exact realtime limit.
- **Node-scoped LTE policy:** Nodes → edit → Traffic supports `cdnMode=standard`
  (no node-specific limit), `all` (every inbound on the node), or `selected`
  with explicit node `cdnInboundTags`. The legacy global inbound list is
  additive for backwards compatibility. A regular node with the same inbound
  tag is not limited merely because a *different* node is marked LTE.
- **Monthly accounting:** Settings → CDN traffic limits → `cdnResetPeriod=monthly`
  activates a calendar-month UTC meter. Signed positive per-user/per-node/
  per-inbound counter deltas are written transactionally during telemetry
  ingestion to `user_inbound_traffic_monthly`. The timestamp source is the
  server's accepted observation time, not a user- or node-supplied date.
  The current month starts at 00:00 UTC on day 1. Historic lifetime totals
  cannot be reliably split into months and are **not backfilled**. Switching
  to monthly mode starts with deltas captured after this migration is installed;
  it does not erase lifetime history. Manually resetting a user's counters also
  resets their monthly ledger totals while preserving the last signed baselines.
- **Single-link use case:** German and Norwegian ordinary nodes plus Polish
  LTE node can share the same subscription, UUID and user: regular user
  `limit=0`, `cdnLimitGb=5`, monthly mode, and Polish node marked `all`
  or `selected`. Hosts and squad access must include all desired entries.
  All limited nodes draw from a shared 5 GiB pool per user; there is no
  per-node 5 GiB allocation.
- **No hard real-time guarantee:** node desired-config reconciliation remains
  asynchronous; an existing Xray connection can outlive reaching the quota.
  Missing/offline telemetry may delay enforcement. If a counter report spans
  the UTC month boundary, its positive delta is attributed to the acceptance
  month; exact within-interval division cannot be reconstructed. Do not
  advertise immediate on-node disconnects or an exact 5.000 GiB hard cap.


### Catalog toolbars and collection actions

**Nodes is the reference composition for catalog controls.** Squads, Hosts,
Templates and Balancers use the same search-left / actions-right hierarchy and
the same primary create-button anatomy. Do not rebuild separate add buttons
in individual feature CSS.

- `workspaceGridControls(kind)`, `workspaceCreateButton(kind,label,id)` and
  `mountWorkspaceGrid(root)` in `frontend/js/core/app.js` are the shared
  renderer/interaction contract. Nodes keeps its existing fleet-specific state
  and buttons but consumes the same visual primitives.
- `.nx-workspace-toolbar`, `.nx-directory-toolbar`, `.nx-workspace-actions`,
  `.nx-workspace-create` and `.nx-workspace-grid-controls` consume global
  material, density, focus, radius and control tokens from the system CSS.
  Feature CSS may adjust only each collection's card geometry and responsive
  reflow.
- All collection toolbars keep the search **first/left** and the create action
  **last/right**. Create actions use an accent icon tile nested inside a quiet
  outlined control; no unrelated feature-specific bright button variants.
- Compact / Standard / Spacious are genuine grid layouts. Their selection is
  saved per collection (`xmeshNexusCollectionView:<kind>`) and never modifies
  records, filtering, pagination, sorting, CRUD or backend configuration.
- Preserve one clearly labelled primary create action per visible catalog,
  and never use the global header's “new user” action as a substitute.
- Balancers show compact readable summary cards and a native expandable editor.
  Saved source selectors, strategy, health probes and SMART opt-in policy
  remain authoritative. Search/density are view-only and must not change the
  submitted settings. Newly created groups open their editor for immediate use.
- Cover English and Russian labels, the 390/768/1920 px breakpoints, browser
  zoom, all three materials and keyboard focus when changing this contract.
- After any UI source change, regenerate the content-addressed keys using
  `node scripts/update-ui-cache.cjs`.

### Empty states / Templates / Balancers

Empty states stay compact and explicit. They do not become half-screen blank cards.

### Editors

Editors own useful working area. Global compaction must not shrink code, chart, JSON or canvas surfaces that benefit from height or width.

## Migration rule

When touching a feature:

1. preserve behavior and data semantics unless explicitly requested;
2. inspect the active importer, renderer and selector ownership before editing CSS;
3. keep material, global tokens, controls and shell in their three system owners;
4. keep Settings, Nodes and other page-specific composition in scoped feature CSS;
5. declare collection, surface and workspace semantics explicitly in markup;
6. avoid DOM-inference builders, global overrides and new presentation layers;
7. retire obsolete source contracts instead of enforcing historical CSS structure;
8. regenerate content-addressed cache keys with `node scripts/update-ui-cache.cjs`.

Do not restore the retired legacy stylesheet or compatibility staging scripts.

## Frontend ownership audit

For every CSS change, review the whole selector scope, not just the screenshot being repaired.

A feature stylesheet is suspicious if it defines any of the following without a feature root:

- `.wrap`;
- `.view`;
- `.app` shell geometry;
- `.card` material;
- `.btn`, `.gh`, `.seg` global visual language;
- `html[data-surface=...]` or equivalent Appearance forks.

The current panel source contract rejects `display: contents` in panel CSS; keep real layout wrappers and their boxes.

## Review checklist

Before merging UI work:

1. Classic / Glass / Raised remain distinct; dark/light themes stay usable.
2. Radius, border, density, content width and motion settings still work.
3. The presentation graph has three system CSS owners plus scoped feature imports.
4. Retired builder, legacy CSS, workspaces module and staging script remain absent.
5. Shared material and global shell selectors stay out of feature CSS.
6. Generic layout stays free of page-specific Settings/Nodes selectors.
7. Settings/Nodes geometry uses feature owners and appropriate container queries.
8. Nodes keeps its approved density caps and action/icon anatomy.
9. No new accent bloom, generic card lift or double material shell is introduced.
10. No accidental dead regions, clipping, overlap or document overflow.
11. Short content remains content-height, while editors retain purposeful workspace.
12. Browser geometry, interactions and screenshots agree with the implementation.

## CI contract

The primary architecture check is:

```bash
node scripts/check-ui-system.js
```

Nodes composition is additionally protected by:

```bash
node scripts/check-node-grid-layout.js
```

The checks enforce content-addressed runtime assets, three system owners plus scoped features, absence of retired implementations, shared material primitives, explicit workspace semantics and feature-scoped Nodes geometry. Browser acceptance lives in `scripts/test-ui-browser.cjs`.
