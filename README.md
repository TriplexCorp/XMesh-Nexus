# XMesh Nexus

**Документация:** **Русский** · [English](README.en.md)

**XMesh Nexus** — самостоятельно размещаемая панель управления VPN-инфраструктурой на базе Xray-core: пользователи, ноды, хосты, сквады, XRAY STUDIO, подписки, мониторинг и администрирование. Backend — **Rust (Tokio/Axum)**; данные — **PostgreSQL 18 + TimescaleDB**, временное состояние — **Redis 7**. Развёртывание панели — через Docker Compose.

> **Статус на 23 октября 2026 года:** проект находится в активной разработке. В репозитории уже есть **публичные маршруты подписок, генерация клиентского Xray JSON, интеграция с управляемыми нодами и сбор реального пользовательского трафика**. Это не значит, что система заработает без настройки: Xray-трафик обрабатывается **на VPS-нодах**, для которых нужен отдельный [XMesh-Node](https://github.com/TriplexCorp/XMesh-Node) и корректная сетевая конфигурация. Наличие кода или интерфейсного переключателя не является доказательством, что конкретный узел получил и применил изменение.

## Что реально реализовано

| Подсистема | Что есть в репозитории | Условия и ограничения |
| --- | --- | --- |
| **Control Plane** | Веб-панель, Rust API, PostgreSQL, управление пользователями, сквадами, хостами, нодами и настройками | Изменения состояния панели не следует путать с подтверждённым состоянием Xray на ноде |
| **XRAY STUDIO** | Редактирование/проверка JSON Xray, инструменты конфигурации, профили и привязки к хостам/нодам | Не каждый протокол конструктора поддерживается публичным генератором подписок |
| **Ноды** | Регистрация с Ed25519, подписанные запросы, heartbeat, выдача желаемой конфигурации, команды перезапуска и обновления | Рабочий Xray и применение конфигурации обеспечиваются отдельными компонентами [XMesh-Node](https://github.com/TriplexCorp/XMesh-Node) |
| **Подписки** | Выпуск и отзыв токенов, публичные URL, HTML-портал, клиентский Xray JSON, выбор RU/EN, определение профиля устройства по User-Agent | Сейчас публичная сборка подключений ориентирована на **VLESS**; требуются валидные пользователи, сквады, профили, адреса и хосты |
| **SUBSCRIPTION STUDIO** | Название/домен, оформление портала, каталог приложений, настройки JSON и балансировщиков | Домен, HTTPS и маршрутизацию до API необходимо настроить самостоятельно |
| **Статистика** | RX/TX узлов, системные метрики, пользовательские и inbound-счётчики, страницы диагностики | Персональные цифры требуют работающего Xray StatsService и корректно установленных агентов |
| **Безопасность** | Роли owner/admin/viewer, серверная авторизация, Argon2, сессии, ограничения входа, TOTP и аудит | Нет гарантии отсутствия уязвимостей; требуется защита VPS, обратного прокси и собственная проверка |
| **IP-пул** | До **256** адресов, проверка формата и повторов, отдельный курсор ротации по паре узел/пользователь | Ротация пока **не встроена** в публичную выдачу клиентских подключений; IP нужно назначить на VPS вручную |

## Как устроена система

- **XMesh Nexus (этот репозиторий)** — панель, API, БД, генератор клиентских подписок, управление конфигурациями и политиками.
- **[XMesh-Node](https://github.com/TriplexCorp/XMesh-Node)** — устанавливаемый на ноды runtime: получение желаемой конфигурации, управляемый Xray, локальная сверка подписанной политики и применение изменений.
- **Linux-агенты метрик и управления** — подключаются к панели исходящими HTTPS-запросами; для управления не нужен публичный входящий API-порт на ноде.
- **PostgreSQL / TimescaleDB** — бизнес-данные, учёт и история метрик внутри одной БД. **Redis** — ограничения частоты запросов и временные данные.
- **Xray-core** на ноде передаёт VPN-трафик. Установленный в контейнере панели бинарник Xray для управления версиями и проверок **не является работающим VPN-входом панели**.

### Важная граница: панель ≠ применённая конфигурация

API предоставляет ноде `POST /api/v1/node/desired-config`: конфигурацию Xray, ревизию и подписанную политику. Отдельный узловой worker должен проверить полученное, протестировать и применить его. **Автоматическое сопоставление локального порта сейчас требует ровно один inbound в назначенном XRAY STUDIO-профиле.** Составные конфигурации с несколькими inbound не следует считать автоматически поддержанными этим путём.

Команды перезапуска/обновления ноды выполняются асинхронно. «Запрос принят» — не «команда успешно выполнена»: проверяйте heartbeat, статус операции и состояние сервиса. Дополнительные сведения: [Автономные ноды и подписанные политики](docs/AUTONOMOUS_NODES.md).

## Установка панели

Необходимы Linux, Docker Engine, Docker Compose plugin, Git и OpenSSL.

```bash
git clone https://github.com/TriplexCorp/XMesh-Nexus.git
cd XMesh-Nexus
chmod +x install.sh
./install.sh
```

Установщик создаёт `.env`, пароли и секреты, запускает контейнеры, выводит первоначальные реквизиты и путь входа. Сохраните их безопасно; **не публикуйте** `.env` или токены подписок.

По умолчанию панель привязана к **`127.0.0.1:8080`**. Для доступа извне настройте **HTTPS reverse proxy**, не открывайте административный API и PostgreSQL/Redis напрямую в интернет. Для продакшена оставьте `COOKIE_SECURE=true`.

```bash
docker compose ps
docker compose logs --tail=100 panel
docker compose logs --tail=100 db
bash xmeshctl
```

`xmeshctl` предоставляет команды проверки, логов, резервного копирования и обновления. **Не используйте `docker compose down -v`** при обычном обновлении: это удаляет постоянные тома.

### Обновление

JavaScript и CSS встроены в Docker-образ. Одного `git pull` для их применения недостаточно:

```bash
git pull --ff-only origin main
docker compose up -d --build
```

Перед обновлением сделайте резервную копию; после — проверьте логи панели и работу нод. Обновление **панели не гарантирует обновление runtime на всех нодах**. Смотрите [обновление панели и телеметрия](docs/PANEL_UPDATE_AND_TELEMETRY.md).

### Резервное копирование

```bash
bash deploy/backup-postgres.sh
```

Храните проверенные копии **вне VPS**. Бэкап PostgreSQL **не включает** `TOTP_ENCRYPTION_KEY` из `.env` и локальный ключ подписи политик нод. Сохраняйте эти ключи отдельно и не перевыпускайте их при обычных обновлениях. Потеря ключей может нарушить вход с 2FA, расшифровку сохранённых ссылок или доверие уже зарегистрированных нод.

## Подписки и клиентский JSON

В Rust реализованы:

- Создание, получение состояния и отзыв пользовательской ссылки: `/api/v1/users/{id}/subscription` (авторизованный API).
- Публичная JSON-выдача: **`GET /api/v1/sub/{token}`**.
- Публичный HTML-портал: **`GET /api/v1/portal/{token}`**; также поддерживается настроенный путь портала.
- Обработка **User-Agent** клиента для выбора профиля транспорта (в частности iOS/Windows) и выдача **нативного Xray JSON**.
- Проверка статуса пользователя: неактивная подписка не выдаёт рабочий клиентский JSON.
- Клиентские конфигурации из связей **пользователь → сквады → inbound XRAY STUDIO → хосты/ноды**, с возможностью JSON-балансировщиков.

**Текущее ограничение:** публичный конструктор outbound в `user_subscriptions.rs` реализован для **VLESS**; наличие VMess, Trojan, Shadowsocks и других протоколов в редакторе XRAY STUDIO **не обещает** их автоматическую выдачу через публичный endpoint. Нативный JSON — поддерживаемый здесь формат подписки; универсальной выдачи URI/base64/Clash/Sing-box форматов нет.

Созданный токен не гарантирует, что настройки уже позволяют построить подключение: API отдельно возвращает признак готовности и предупреждение. Для публичного домена нужны DNS, действующий TLS-сертификат и корректный прокси до панели. **Не путайте сохранённый URL с проверенной доступностью VPN.**

### SUBSCRIPTION STUDIO

Можно настроить оформление действующего портала: RU/EN, название, подписи, цвета, логотип, блоки статуса/трафика/срока, QR, поддержку и клиентские приложения, включая свои. Публичный шаблон HTML и JavaScript находится в **этом** репозитории, а не только в отдельной будущей реализации. Предпросмотр в студии остаётся предпросмотром; фактический результат зависит от сохранённых настроек и работающего endpoint.

## Ноды, лимиты и статистика

**Ноды:** сервер выдаёт подписанный policy envelope с контрольной суммой конфигурации. Узловой worker из XMesh-Node проверяет его и хранит последний применённый экземпляр. Локальный механизм может применять истечение срока и ограничение трафика, когда панель недоступна. Это **не математически точный общий лимит** на нескольких отключённых нодах: используются консервативные локальные бюджеты, а синхронизация может запаздывать. Проверяйте реальное прекращение трафика на тестовом UUID; не считайте визуальный статус «отключён» подтверждением блокировки.

**Статистика узла:** Linux-агент передаёт CPU, RAM, диск и сетевые RX/TX в TimescaleDB. Скорость сетевого интерфейса может включать SSH и другой трафик и **не является расходом конкретного пользователя**.

**Статистика пользователя:** учитывается отдельно из **Xray StatsService** через локальный сборщик, связанный с пользователем, inbound и нодой. Требуются рабочий управляемый Xray, локальный API статистики и актуальные агенты. Первый достоверный снимок задаёт начальную точку учёта; исторические байты до этого не восстанавливаются. Если счётчики недоступны, это не означает нулевой расход.

Инструкции: [подключение автономных нод](docs/AUTONOMOUS_NODES.md), [обновление телеметрии и персональный учёт](docs/PANEL_UPDATE_AND_TELEMETRY.md), [идентичность узлов и Ed25519](docs/SECURITY_NODE_IDENTITY.md).

### IP-ротация

В редакторе ноды поддерживается **2–256 уникальных публичных IPv4/IPv6** при включённой ротации. Все адреса должны быть фактически настроены на VPS и обслуживать соответствующее подключение. **Текущее ограничение backend — 4096 байт на текстовое поле пула**, поэтому список из 256 длинных IPv6-адресов может не пройти проверку даже при допустимом числе строк.

Курсор round-robin по `(node_id, user_id)` сохраняется в PostgreSQL. Для авторизованной проверки есть `POST /api/v1/nodes/{id}/rotation/next`. Но **в текущем публичном обработчике подписок этот механизм не вызывается**: автоматическое переключение IP при обновлении подписки не следует считать готовой функцией.

## Администрирование и безопасность

- Роли **owner / admin / viewer** и серверная проверка полномочий.
- Argon2 для паролей, сессии с HttpOnly/SameSite-cookie, ограничения попыток входа, аудит.
- Необязательная **TOTP 2FA** (совместимые приложения-аутентификаторы, одноразовые резервные коды).
- Настройки срока сессии, таймаута бездействия и ограничений одновременных сессий.
- Отдельный путь `/dashboard/...` для входа. Он **не заменяет авторизацию** или сетевые ограничения; не считайте скрытый URL механизмом безопасности.
- Авторизация узлов на основе **Ed25519-подписей** и защита от повторного использования запросов.

**Не заявляем:** завершённый аудит безопасности всей инфраструктуры, отсутствие известных/неизвестных уязвимостей, стопроцентную корректность выдачи квот при сетевых разделениях или полноту реализации всех протоколов Xray.

Актуальные детали и известные риски: [аудит безопасности от 22 октября 2026](docs/SECURITY_AUDIT_2026-10-22.md), [технический долг](docs/TECH_DEBT_AUDIT.md).

## Интерфейс и инструменты разработки

В панели есть RU/EN, светлые/тёмные темы, палитры/HEX, анимации, параметры плотности и размера, карточки и статистика. Эти настройки в основном относятся к **отображению**, а не к поведению Xray.

Для локальных проверок фронтенда используйте **Node.js 24** (в продакшене фронтенд выполняется в браузере, backend — Rust):

```bash
node --check app.js
node scripts/check-node-ip-rotation.js
node scripts/check-node-editor-layout.js
node scripts/check-subscription-studio.js
node scripts/check-static-assets.js
cargo test --manifest-path backend/Cargo.toml
```

Основные файлы: `app.js`, `styles.css`, `xray-studio-v4.js`, `subscription-studio.js`, `backend/src/`, `deploy/`, `scripts/`. Тестовые скрипты и CI проверяют часть сценариев, **но не заменяют проверку настоящего Xray на VPS и приложения клиента**.

## Известные границы (кратко)

1. **Управляемой ноде нужен установленный XMesh-Node и корректный реальный Xray.** Изменение формы панели само по себе не подтверждает применение конфигурации.
2. **Публичная подписка есть, но генерация подключений пока VLESS-ориентированная и JSON-ориентированная.** Произвольные протоколы конструктора не выдаются автоматически.
3. **IP-ротация хранится и тестируется, но не подключена к публичной выдаче.**
4. **Общий офлайн-лимит между несколькими нодами не строгий.** Для финансово-критичных квот нужны дополнительные гарантии.
5. **Нужно настраивать DNS, HTTPS reverse proxy, сеть VPS, IP-адреса и обновлять агентов.**
6. **Достоверность метрик зависит от источника:** RX/TX интерфейса ≠ персональные счётчики Xray.
